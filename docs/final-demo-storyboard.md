## 1. 故事的核心

### 主角

一位刚结束会议、准备开车接孩子的在职家长。故事板不虚构姓名、年龄、公司或家庭隐私；现场统一称为“用户”或“家长”。

### 主角真正想完成的事

用户不是想体验一个 AI 功能，而是想在安全驾驶的同时守住“按时接孩子”这项刚性责任，并把“去超市”这项弹性任务妥善处理。

### 冲突

会议延迟已经压缩最晚出发时间，晚高峰又让预计到达时间变成 18:28。继续催促、加速或展示更多信息都不能解决现实后果，反而会增加驾驶干扰。

### AURI 的角色

用户是故事主角，AURI 是可靠的协助者。它不替用户驾驶、不诊断情绪，也不擅自执行高风险动作；它负责理解自然语言、保护刚性责任、准备现实行动，并在正确设备上请求一次确认。

### 情绪弧线

有安排 → 开始担心 → 责任可能失约 → 感到被理解和支持 → 一次确认后放下负担 → 停车后重新掌控全貌。

### 一句话故事

**AURI 没有让拥堵消失，但它让用户不用一边开车，一边独自处理迟到带来的所有后果。**

|---|---|---|---|---|---|

| 2. 时间窗口被压缩 | 问题出现 | 开始担心 | 手机 + 腕表 | pre_departure_warning / L1 | 系统在失约前提前介入 |

## 3. 六格详细故事板

### 画面 1：出发前的安排

**时间**

0:00–0:25。

**叙事作用**

介绍主角、日常场景和两项不同性质的责任。观众先理解“这是一个真实生活压力问题”，而不是先看技术。

**画面构图**

- 中景：用户在会议结束前或办公区域收拾东西，手机在手中。
- 手机特写：AURI 输入页与今日任务页。
- 背景只保留办公环境线索，不出现真实公司、联系人或地址。
- 画面角落可以出现简洁的时间标记“17:40”。

**用户动作**

用户按住语音按钮，说：

> 今天 18:10 接孩子，之后去超市。

如果现场环境嘈杂，用户改用文字输入同一句话，叙事不受影响。

**屏幕重点**

- 任务一：18:10 接孩子。
- 责任属性：刚性、不可随意后置。
- 任务二：去超市。
- 责任属性：弹性、可替代。
- 状态：已同步。

**讲解词**

> 这是一位刚结束工作的家长。他今天有两件事：18:10 接孩子，之后去超市。AURI 先理解哪件事不能失约，哪件事可以换一种完成方式。

**幕后事件**

- 手机提交自然语言或标准任务事件。
- Agent 生成结构化 Task。
- 后端写入唯一 World State。
- 控制台、车机预加载端和手机使用同一个 session_id。

**要证明的产品价值**

AURI 理解的不是两个普通提醒，而是“刚性责任”和“弹性任务”的差异。

**验收信号**

- 手机显示两个结构化任务。
- 控制台能看到同一 session、revision 和任务。
- 此时车机不抢交互，腕表不震动。

**导演注意**

不要在第一格解释 LangChain、Schema 或工具调用。先让观众认识用户和责任。

---

### 画面 2：时间窗口被压缩

**时间**

0:25–0:55。

**叙事作用**

问题出现。用户还没有真正迟到，但余量正在消失；AURI 在危机发生前介入。

**画面构图**

- 用户仍在会议或刚离开会议室，墙上时钟或手机时间向后推进。
- 手机出现低干扰风险卡。
- 腕表特写进入黄色 warning 状态。
- 车机画面保持安静或只显示预加载，不出现确认。

**幕后操作**

控制台导演点击“会议延迟 20 分钟”。

**屏幕与触觉重点**

- 风险等级：L1。
- 文案：最晚出发窗口正在被压缩。
- reason_codes 显示会议延迟与出发余量下降。
- 腕表只双短震一次。

**讲解词**

> 会议比计划晚了 20 分钟。AURI 没有等到真正失约才报警，而是在最晚出发窗口被压缩时，用手机和一次腕上触觉轻提醒。

**用户反应**

用户看一眼提示，收起手机，开始前往车辆。表情是“开始担心”，不是夸张焦虑。

**要证明的产品价值**

系统能够提前识别责任风险，同时控制打扰强度。

**验收信号**

- stage 进入 pre_departure_warning。
- pressure_level 为 L1。
- primary_surface 仍是 mobile。
- 腕表相同 command_id 不重复震动。
- 车机没有可操作确认入口。

**导演注意**

不要说“手表检测到用户焦虑”。本轮只能说会议和时间窗口构成主要风险，腕上信号最多是辅助信息。

---

### 画面 3：预计晚到 18 分钟

**时间**

0:55–2:10。

**叙事作用**

这是故事的“Oh Crap”时刻：用户已经进入车辆，晚高峰使接孩子预计晚到 18 分钟。用户不能一边开车一边打电话、发消息、改行程和采购。

**画面构图**

- 主画面切到横屏车机。
- 手机退到 Companion 只读状态并离开用户手中。
- 腕表进入 handover 或 processing，但不显示复杂内容。
- 车机显示学校任务、ETA 18:28、预计晚到 18 分钟。
- 用户双手保持驾驶姿态。

**幕后操作顺序**

1. 控制台注入接近车辆。
2. 控制台注入进入车辆。
3. 控制台注入晚高峰拥堵和 ETA 18:28。

**用户台词**

> 我还来得及吗？帮我处理。

**车机结论**

> 预计晚到 18 分钟。继续加速无法明显解决问题。

**讲解词**

> 上车后，主交互端自动交给车机，手机退出确认。晚高峰让预计到达时间变成 18:28。真正的压力不是“还有多远”，而是接孩子这项责任可能失约，而用户正在驾驶，无法同时处理这些后果。

**要证明的产品价值**

AURI 知道此刻不该继续增加提醒，而应该接管可被安全处理的现实后果。

**验收信号**

- primary_surface 在 1 秒内变为 vehicle_hmi。
- 手机确认入口失效。
- pressure_level 为 L2，late_minutes 为 18。
- 车机只有一条风险结论，不出现消息全文或商品长列表。

**导演注意**

这是全场情绪最高点。主持人说完后停顿 1 秒，让观众看到 ETA 和用户无法分心的处境。

---

### 画面 4：方案出现

**时间**

2:10–3:05。

**叙事作用**

AURI 出现为协助者。它不是“替用户做一切”，而是把复杂后果整理成一个可理解、可确认的方案。

**画面构图**

- 车机为主画面，AURI 使用克制的深蓝背景和低频光晕。
- 左侧或上方只有一条结论。
- 中间是一个动作组摘要。
- 下方只有一个“确认处理”入口。
- 手机可在副屏展示完整明细，但驾驶中的用户不操作它。

**AURI 对用户的回应**

> 接孩子这件事我会优先保护，你先安全驾驶。我已准备通知老师和家人的消息，并把超市任务改为模拟配送方案。

**动作组摘要**

- 通知老师预计晚到 18 分钟。
- 同步家人当前接送进度。
- 将去超市替换为模拟 grocery delivery。
- 显示商品数量、总价和配送时段。
- 所有外部消息和订单明确标注“模拟”。

**讲解词**

> AURI 先保护不可后置的接孩子任务，再把去超市换成配送。它已经把消息和订单方案准备好，但没有擅自发送或下单。驾驶中只给用户一条结论、一个动作组和一个确认。

**用户反应**

用户听完后明显从“需要自己处理很多事”变为“只需要判断这一个方案是否可以”。

**要证明的产品价值**

Agent 的价值不是生成更多文字，而是把复杂责任推进到可确认的现实行动。

**验收信号**

- stage 从 planning 进入 waiting_confirmation。
- confirmation status 为 pending。
- confirmation owner 为 vehicle_hmi。
- 手机和腕表都没有可点击确认。
- 订单未确认前仍为 awaiting_confirmation。

**导演注意**

不要展示 LangChain 的思维过程。可以在技术附录展示工具名，但主故事只展示对用户有意义的结果。

---

### 画面 5：一次确认后的顿悟

**时间**

3:05–3:50。

**叙事作用**

这是“Aha”时刻。用户发现自己不需要在驾驶中逐条处理消息和采购，只需要在正确设备上做一次安全确认。

**画面构图**

- 车机特写：唯一大按钮“确认处理”。
- 用户用按钮或语音二选一确认，不同时演示两种方式。
- 车机进入 executing，随后显示完成结论。
- 腕表变绿并柔和短震一次。
- 手机保持只读同步。

**用户动作**

用户点击一次“确认处理”，或说：

> 确认处理。

**执行结果**

- 老师消息：模拟发送完成。
- 家人消息：模拟发送完成。
- 配送订单：模拟提交完成。
- Action Ledger 写入唯一结果。
- 系统进入 cooldown。

**车机完成文案**

> 已处理。你按当前速度安全驾驶即可。

**讲解词**

> 用户只确认一次。消息与预算内的低风险模拟订单被幂等执行，重复点击也不会产生第二条消息或第二个订单。完成后 AURI 立即降低打扰，把注意力还给驾驶。

**用户反应**

用户不需要庆祝或与 AI 继续聊天，只是松一口气，把注意力稳定地放回道路。

**要证明的产品价值**

真正的突破是“责任后果被安全处理”，而不是用户看到了一个智能界面。

**验收信号**

- 相同 confirmation_id 只执行一次。
- 只有一个 order_id。
- 三端在 1 秒内同步完成状态。
- 腕表只震动一次。
- 完成播报只出现一次，随后进入 cooldown。

**导演注意**

不要在主故事里故意双击。重复确认放到 60 秒技术证明环节。

---

### 画面 6：停车后重新掌控

**时间**

3:50–4:20。

**叙事作用**

展示“使用后的生活状态”。AURI 没有取代用户，而是在高负荷时接住复杂责任，停车后把完整控制权和解释交还给用户。

**画面构图**

- 用户已停车，手机重新成为主设备。
- 手机复盘页展示一条清晰时间线。
- 车机进入安静结束态，腕表恢复 idle。
- 用户查看结果后锁屏离开车辆。

**手机复盘内容**

- 原始任务：18:10 接孩子、去超市。
- 风险原因：会议延迟、晚高峰、预计晚到 18 分钟。
- 任务调整：超市改为模拟配送。
- 消息结果：老师与家人消息模拟完成。
- 订单结果：商品、金额、配送时段和 order_id。
- Action Ledger：准备、确认、执行、完成。
- 如使用 fallback，明确记录降级方式。

**讲解词**

> 停车后，完整控制权回到手机。用户可以看到 AURI 为什么介入、准备了什么、确认了什么、最终执行了什么。整个过程可解释、可追踪，也可以复盘。

**用户反应**

用户确认重要责任已经被保护，知道下一步只需继续接孩子，不再被超市、消息和订单同时占用注意力。

**要证明的产品价值**

“压力接管”不是替用户做主，而是在正确时机减少认知负担，并在事后保留完整透明度。

**验收信号**

- stage 为 parked_review。
- primary_surface 回到 mobile。
- 复盘内容全部来自真实 World State 和 Ledger。
- 不出现虚构的成功记录、内部 prompt 或敏感凭据。

**导演注意**

最后停在用户结果，不要再回到技术控制台。技术架构放到主故事结束后的附录。

## 5. 舞台与镜头布局

### 推荐舞台

- 中间大屏：车机 HMI，是驾驶阶段的主要视觉中心。
- 左侧竖屏：手机投屏，用于开场任务和结尾复盘。
- 右上角小窗：真实腕表摄像机特写，只在 L1、handover、completed 时出现。
- 控制台：由导演在侧台操作，主故事中不持续投给观众。
- 技术状态轨：可选，只显示 session、revision、stage、primary_surface，不展示 Token。

### 镜头原则

- 每一格只突出一个情绪和一个产品价值。
- 进入车辆后，不拍用户手持手机。
- 车机确认按钮必须足够大，画面中不能出现多个竞争 CTA。
- 腕表震动需要用表盘变化、字幕或现场讲解辅助表达。
- 模拟消息和订单始终带“模拟”标签。

## 6. 视觉制作说明

### 六格静态故事板版式

- 画布：16:9 横向，可做成一页六格或两页三格。
- 顺序：从左到右、从上到下。
- 每格包含：场景草图、画面标题、一句用户处境、一句 AURI 价值。
- 情绪色：平静深蓝 → 风险黄 → L2 蓝紫 → 完成绿。
- 品牌：海军蓝为主、象牙白留白、品牌金只做识别，不替代风险黄。
- 角色：使用克制的真人轮廓或简笔画，不使用拟人机器人和夸张焦虑表情。
- AURI：以界面、光晕和状态变化出现，不画成会说话的 3D 角色。

### 每格海报短句

1. **我先把今天的责任安排好。**
2. **时间正在变紧，但还来得及提前处理。**
3. **我不能一边开车，一边处理所有后果。**
4. **接孩子优先，其他事情我先帮你准备好。**
5. **确认一次，剩下的按规则处理。**
6. **停车后，每一步都看得见。**

## 7. 60 秒技术证明附录

主故事结束后，只选择一个安全能力和一个跨端能力，不再完整重演故事。

### 证明 A：确认幂等

1. 在 waiting_confirmation 状态记录 confirmation_id。
2. 同时触发按钮确认和重复请求。
3. 控制台展示 duplicate 或相同 revision。
4. Ledger 中只有一份动作结果和一个 order_id。

### 证明 B：唯一主交互端

1. 展示 vehicle_hmi 为 primary_surface。
2. 手机上旧确认入口已隐藏或失效。
3. 手机尝试确认时后端返回 WRONG_SURFACE。
4. 车机使用同一 confirmation_id 成功确认。

### 技术讲解口径

> 大模型负责理解用户自然语言和选择受控工具；确定性后端负责风险等级、主交互端、预算、权限、确认和最终状态。因此 AURI 可以有自然语言的温度，但关键行为仍可测试、可重复、可审计。

## 8. 真实、模拟与降级边界

### 真实运行

- 手机、车机和腕表 UI。
- 自然语言输入和 Agent 工具选择。
- Task、Risk、World State、primary_surface 和 revision。
- 方案准备、确认 owner、幂等、广播和 Ledger。
- 腕表真实显示、触觉和 ACK。

### 可控模拟

- 会议延迟、进入车辆、交通和 ETA。
- 老师/家人消息发送结果。
- 商品、价格、库存、配送和订单提交结果。

### 现场降级

| 故障 | 降级方式 | 必须如何说明 |
|---|---|---|
| ASR 失败 | 使用同一句文字输入 | “语音识别降级为文字，Agent 主链路不变” |
| LLM 超时 | 使用确定性 parser 完成固定场景 | 界面明确显示 fallback |
| SSE 中断 | 自动轮询并拉取最新快照 | 显示“轮询模式” |
| 腕表断连 | 主流程继续，腕表显示离线 | 不能把本地 Debug 说成实时联动 |
| Render 休眠 | 演示前 10 分钟预热 | 主持人不在台上等待服务唤醒 |

## 9. 现场角色分工

| 角色 | 责任 |
|---|---|
| 主持人 | 讲人物、问题和结果，不讲过多实现细节 |
| 用户演员 | 说固定任务、求助和确认语句；驾驶阶段不碰手机 |
| 控制台导演 | 按导演表注入外部事件，观察 stage 和 revision |
| 技术保障 | 监控 Render、网络、日志和备用方案，不同时操作主 Session |
| 腕表镜头 | 保证 warning 和 completed 两次关键触觉被观众看到 |

## 10. 故事板验收

### 叙事验收

- [ ] 观众能在 20 秒内理解主角是谁、要完成什么。
- [ ] 第三格的危机来自真实责任失约，而不是抽象“效率低”。
- [ ] AURI 的出现自然：用户明确求助后才进入协调接管。
- [ ] 第五格的顿悟是现实后果得到处理，不是“界面很智能”。
- [ ] 第六格具体展示更好的结果和完整透明度。

### 产品验收

- [ ] 六格中的所有状态都能由正式 Event 和 World State 产生。
- [ ] 驾驶中只有车机拥有确认入口。
- [ ] 腕表不进行长对话，也不直接决定 L0–L3。
- [ ] 未确认前不发送消息、不提交订单。
- [ ] 重复确认只执行一次。
- [ ] 停车复盘全部来自真实 Ledger。

### 表演验收

- [ ] 完整主故事不超过 4 分 20 秒。
- [ ] 主持人、用户和控制台导演各自只执行固定动作。
- [ ] 关键文案、设备切换和腕表触觉经过至少 3 次场地彩排。
- [ ] 准备录屏、文字输入、轮询和离线夹具等备份。

故事板是否成功，不以“展示了多少页面”为判断，而以观众是否清楚感受到这条变化为判断：

**用户从“驾驶中必须独自处理多个责任后果”，变成“只需安全确认一次，停车后仍能掌控和复盘全部结果”。**
